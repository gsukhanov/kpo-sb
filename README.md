В этой ветке находится проект по ДЗ2 по КПО.

Проект реализован на Java со сборкой через Gradle с использованием Spring Boot

Для запуска используйте ./gradlew runBoot или запустите файл BankApplication.

В этом проекте нет ни одной строки сгенерированного кода, он весь был написан моими руками (и именно поэтому с задержкой на 8 дней...)

В проекте реализовано модельное консольное приложение для работы с базой данных банка
Функционал приложения:
1. Добавление/удаление аккаунтов, категорий и операций в базу данных в кэше приложения.
2. Аналитика для аккаунтов: информация о балансе, изменении за определенный период и по отдельной категории.
3. Загрузка базы данных из файла в кэш и выгрузка из кэша в файл форматов .csv и .json.
4. Телеметрия команд - вывод, сколько времени заняло исполнение команды.
5. Настройка приложения.

В проекте реализуются принципы SOLID:
1. Single responsibility - каждый класс отвечает за свою область. Так, команды выполняют ровно одну функцию, Timer - только за замер времени, Streamer отвечает за сериализацию и десериализацию, фабрики - за создание объектов, фасады - за взаимодействие с базами данных, модели - за хранение данных, Runner - за консоль, runner/auxillary-классы - за отдельные пункты консольного меню.
2. Open/Closed - существует интерфейс ICommand, и для добавления команды достаточно его имплементировать и добавить фабричный метод в Invoker, вся остальная логика не изменится.
3. Liskov substitution - наследники ICommand используются повсеместно именно вызывая их метод execute()
4. Interface segregation - интерфейс ICommand не требует от команд уметь что-либо, кроме как исполнение и вывод собственного имени.
5. Dependency inversion - взаимодействие с командами идет через интерфейс Invoker, не зависящий от реализации конкретных команд, а взаимодействие с фасадами - через IFacade, абстрагирующий от конкретной реализации фасадов.

В проекте реализуются принципы GRASP:
1. Information expert - фасады хранят в себе базы данных и работают с ними, а Streamer работает с JSON и CSV, файлами и базами данных, организует сериализацию и десериализацию.
2. Creator - команды создания, делегирующие полномочия фабрикам и Invoker, создающий команды.
3. Controller - консольный интерфейс внутри ConsoleRunner, разделенный на слои - Executor для исполнения команд и обертки их в таймер, Database для команд добавления и удаления из БД, Analytics для команд аналитики, Streaming для сериализации/десериализации и Settings для настройки.
4. Low Coupling - пользовательский интерфейс не имеет отношения к реализации бэка, а многие команды не зависят от других частей кода.
5. High Cohesion - классы имеют четко очерченный функционал, и разделены по пакетам. Это верно для всего проекта, тут даже сложно конкретный пример привести.
6. Polymorphism - команды в полной мере реализуют полиморфизм, из-за чего Executor и Timer не интересует, какую команду они получили на вход.
7. Pure Fabrication - Invoker является чистой выдумкой, нужной мне для удобства реализации системы команд.
8. Indirection - собственно тот же Invoker является посредником между системой команд и остальными классами. Также Streamer - это посредник между кэшем приложения и файловой системой.
9. Protected Variations - через ICommand можно менять реализацию команд, не меняя работу Executor и Timer.

В проекте используются следующие шаблоны проектирования:
1. Фасад. Для взаимодействия с базами данных в кэше, используются фасады с общим интерфейсом
2. Команда. Практически все взаимодействия между классами, а также с консолью, реализованы через команды.
3. Декоратор. Класс Timer является декоратором, принимающим на вход команду, и сохраняющим время её работы, пробрасывая результат.
4. Цепочка обязанностей. Взаимодействие с командами происходит не напрямую, а через интерфейс Invoker, который преобразует запрос, достает из него требуемые данные и возвращает нужную команду, упрощающий создание команды, и возвращает команду.
5. Шаблонный метод. Интерфейс ICommand имеет шаблонный метод Object execute(), позволяющий абстрагироваться от конкретного требования. Это применяется при загрузке и выгрузке - Invoker решает по виду запроса, какой класс и в какой формат необходимо выгрузить.
6. Посетитель. Класс Streamer, выгружающий и загружающий базы данных, является посетителем - он через фасад получает доступ к базам данных и затем вызывает нужную команду для каждого элемента базы данных.
7. Фабрика. Создание элементов баз данных отдано фабрике. Класс Invoker тоже по сути является фабрикой команд, а все его методы - фабричные.
8. Синглетон. Фабрики и фасады в моём проекте являются синглетонами, так как базы данных должны существовать в единственном экземпляре, а идентификаторы элементов баз данных не должны повторяться. Чтобы не допустить множественных баз данных, а также хранить в памяти проекта идентификаторы объектов для избегания пересечений идентификаторов, используется синглетон, реализованный через enum.
